# NetChaos – per-module reference

Detailed notes for each module (topology, traffic, chaos, detection, recovery, ...). Storage is **MongoDB** (PyMongo) plus an in-memory NetworkX graph. The end-to-end lifecycle and what has been verified are in the top-level [README](../README.md).

## Endpoints

| Method | Path |
|---|---|
| POST, GET | `/api/networks` |
| GET | `/api/networks/{network_id}` |
| POST, GET | `/api/networks/{network_id}/nodes` |
| GET, DELETE | `/api/networks/{network_id}/nodes/{node_id}` |
| POST, GET | `/api/networks/{network_id}/links` |
| GET, DELETE | `/api/networks/{network_id}/links/{link_id}` |
| POST | `/api/networks/{network_id}/templates/{linear\|star\|ring\|mesh}` |
| GET | `/api/networks/{network_id}/topology` |
| GET | `/health` |

Errors always look like `{"error": {"code": "...", "message": "...", "details": [...]}}`:
400 invalid input (`invalid_node_type`, `invalid_bandwidth`, `invalid_latency`, `invalid_packet_loss`, ...),
404 `network_not_found` / `node_not_found` / `link_not_found`, 409 `duplicate_node` / `duplicate_link` / `network_not_empty`.

## Design decisions and limitations

- **Ids** (`net_001`, `node_001`, `link_001`) are generated by the server. Node/link numbers are per network and never reused. Because ids are server-generated, "duplicate node id" cannot occur; duplicates are enforced on **node name per network** and on **node pairs** (one link per pair).
- **Links are undirected** (a `networkx.Graph`), so A–B and B–A are the same link; self-links and parallel links are rejected.
- **Deleting a node deletes its links** (database cascade and graph). There is no delete-network endpoint yet; deleting a network row in SQL cascades to its nodes and links.
- **Single process only.** The graph is process memory, rebuilt lazily from MongoDB on first use after a restart. Run one uvicorn worker; multiple workers would each hold a separate, unsynchronised graph.
- Network id generation is not safe against two simultaneous creations (the loser gets a 409 and retries).
- No migration tool: indexes are created on start-up (`init_db`); documents are schemaless.
- Timestamps are UTC without a timezone suffix.

## Interface for later modules

```python
TopologyService(db, graph_manager).snapshot_graph(network_id)   # loads the graph from MongoDB if needed, returns a locked copy
G.nodes[node_id]   # name, type, status, created_at
G[u][v]            # link_id, bandwidth (Mbps), latency (ms), packet_loss (%), status
```
Mutations must go through `TopologyService` so MongoDB and the graph stay in step. Module 2 reads the graph
only through `snapshot_graph` (added for it; it wraps `_ensure_graph` + `GraphManager.snapshot`).

# Module 2 – Traffic Simulation

## 1. What it does

It sends a burst of packets from a source node to a destination node through the topology from Module 1
and reports what happened: the route, hop count, latency, bottleneck bandwidth, packets delivered/dropped and
throughput. It is a **controlled, deterministic model**, not a measurement of real network behaviour: there is
no real traffic, and the same topology + parameters + seed always give the same result.

```
create (pending) ──► run ──► route ─► packets ─► metrics ─► stored (completed | failed)
```

Code layout: `api/traffic.py` (HTTP) → `services/traffic_service.py` (validation, persistence) →
`simulation/traffic_simulator.py` (all the maths, no FastAPI imports) · `schemas/traffic.py`.

## 2. How routes are calculated

At run time the simulator takes one snapshot of the network's NetworkX graph (inserted in sorted order so ties are
broken the same way every time) and calls `networkx.shortest_path`, i.e. the **fewest hops**. The route is stored with
the simulation. If no route exists the simulation ends as `failed` with `"No route available between source and destination"`.
Since Module 3 the route is calculated over the *whole* topology, failed nodes and links included, and then checked:
if it crosses a failed element the simulation fails with `"Current route contains failed node"` / `"... failed link"`
(see [Module 3](#7-how-chaos-interacts-with-traffic-simulation)). **There is no rerouting.**
Any node can forward traffic (hosts included), and the route is calculated when the simulation *runs*, not when
it is created, so it always reflects the topology at that moment.

## 3. Latency and hop count

`path_latency_ms` = sum of the `latency` of every link on the route (`calculate_route_latency`).
`hop_count` = number of links (not nodes). 10 + 20 + 30 ms over A→B→C→D gives 60 ms and 3 hops.

## 4. Packet loss

Every packet crossing a link is dropped with probability `packet_loss / 100` of that link, decided with
`random.Random(random_seed)`; one random number is drawn per link crossed, in route order. A dropped packet
goes no further (it still occupied the link while being sent). Overall loss therefore compounds across links
(two 10 % links lose about 19 %). If `random_seed` is omitted the server generates one **and stores it**, so
every run can be reproduced afterwards.

## 5. Bandwidth

`path_bandwidth_mbps` = the smallest link `bandwidth` on the route (the bottleneck): 100, 50, 80 Mbps gives 50.

## 6. Simulated time and throughput

All packets wait at the source at t = 0 and are sent back to back. Each link is a store-and-forward stage:

```
tx_time_ms   = packet_size_bytes * 8 / (bandwidth_mbps * 1000)
start        = max(time packet is ready at the node, time the link becomes free)
link busy    = start .. start + tx_time
ready next   = start + tx_time + link.latency + 0.05 ms processing overhead
```

`simulated_duration_ms` is the model time at which the last packet was delivered or dropped.
`execution_duration_ms` is how long the Python code really took; the two are unrelated.

```
throughput_mbps = delivered_packets * packet_size * 8 / (simulated_duration_ms * 1000)
```

Throughput is therefore always below the bottleneck bandwidth (the first packet also has to cross the
latency of the whole path) and is 0 when nothing is delivered. Assumptions: links are full duplex, queues are
unlimited, there is no send-rate limit and no congestion model.

## 7. Create and run a simulation

```bash
J='-H content-type:application/json'; API=http://localhost:8000/api/networks
# 1. create -> 201, status "pending" (random_seed optional, store_packets optional)
curl -XPOST $API/net_001/traffic/simulations $J -d \
 '{"source":"node_001","destination":"node_004","packet_count":1000,"packet_size":1024,"random_seed":42}'
# 2. run -> 200, status "completed" (or "failed" + failure_reason)
curl -XPOST $API/net_001/traffic/simulations/sim_001/run
# 3. read back
curl $API/net_001/traffic/simulations                        # history, newest first
curl $API/net_001/traffic/simulations/sim_001
curl $API/net_001/traffic/simulations/sim_001/metrics        # 409 until it has run
curl "$API/net_001/traffic/simulations/sim_001/packets?limit=100&offset=0"   # only if store_packets was true
```

Only a `pending` simulation can run. Running a finished one returns 409 (`simulation_already_finished`)
so old results are never overwritten; **create a new simulation to run again** (useful after the topology changes).

Real output for the topology Router-A -100 Mbps/10 ms- Router-B -50 Mbps/15 ms/10 % loss- Router-C -100 Mbps/20 ms- Server-D:

```json
{
  "simulation_id": "sim_001", "network_id": "net_001",
  "source": "node_001", "destination": "node_004",
  "packet_count": 1000, "packet_size": 1024, "random_seed": 42, "status": "completed",
  "route": ["node_001", "node_002", "node_003", "node_004"], "route_available": true,
  "delivered_packets": 906, "dropped_packets": 94, "packet_loss_percentage": 9.4,
  "path_latency_ms": 45.0, "hop_count": 3, "path_bandwidth_mbps": 50.0,
  "throughput_mbps": 35.485612, "simulated_duration_ms": 209.15384, "execution_duration_ms": 1.92
}
```

Check: 906 × 1024 × 8 / (209.15384 × 1000) = 35.4856 Mbps.

## 8. Endpoints and errors

| Method | Path (prefix `/api/networks/{network_id}/traffic/simulations`) |
|---|---|
| POST, GET | `` (create, history) |
| GET | `/{simulation_id}` |
| POST | `/{simulation_id}/run` |
| GET | `/{simulation_id}/metrics` |
| GET | `/{simulation_id}/packets` (optional packet records) |

Errors use the same JSON shape as Module 1. 400 `same_source_destination`, `invalid_packet_count`,
`invalid_packet_size`, `invalid_random_seed`, `invalid_store_packets`; 404 `network_not_found`, `node_not_found`,
`simulation_not_found`; 409 `simulation_already_running`, `simulation_already_finished`, `metrics_not_available`.
Limits: 1 to 100,000 packets, 1 to 65,535 bytes. Module 1 reports *all* request-validation failures as 400
(not FastAPI's default 422) and Module 2 keeps that convention.

## 9. Database and packet records

`traffic_simulations` holds one row per simulation: parameters, seed, status, the route (JSON) and every summary metric.
`packets` holds one row per packet **only** if the simulation was created with `"store_packets": true`, and only for
simulations of up to 1,000 packets (`TRAFFIC_MAX_STORED_PACKETS`). Reason: everything the dashboard needs is in the summary
row, and a 10,000-packet run would otherwise insert 10,000 rows for nothing. Packet rows are inserted in batches of 500 in
the same transaction as the summary. Simulations have no foreign key to nodes, so deleting a node keeps the history.
Metrics are stored as BSON doubles, so stored values equal the API response.

## 10. Dashboard

Sidebar **Traffic Simulation** form (Create, then Run the selected pending simulation); a **Traffic Result** panel and a
**Simulation History** table under the topology. Selecting a history row shows its metrics and highlights its route in violet on the
topology. History is loaded from the server, so it survives a page refresh or a backend restart.

## 11. Deliberately not implemented in Module 2

Failure detection, automatic rerouting and alternative paths, recovery time, resilience score, WebSockets and packet
animation. (Chaos injection was added by [Module 3](#module-3--chaos-injection).)

# Module 3 – Chaos Injection

## 1. What it does

It lets you deliberately break or degrade the **existing** network and then observe the effect with Module 2:

```
Existing network ─► pick a scenario ─► apply chaos ─► the real nodes/links change ─► run traffic ─► observe ─► revert
```

Chaos writes to the same `nodes`/`links` rows and the same NetworkX graph that Modules 1 and 2 use. There is no
separate "chaos graph" and no fabricated "chaos result": the traffic simulator simply reads the current topology.
Nothing recovers by itself and nothing is rerouted; you undo chaos explicitly with **Revert** or **Reset**.

Code layout: `api/chaos.py` (HTTP) → `services/chaos_service.py` (validation, transactions, graph sync) →
`chaos/state.py` (pure state maths, no FastAPI) · `schemas/chaos.py`.

## 2. Supported scenarios

| Scenario | Endpoint (under `/api/networks/{network_id}/chaos`) | Effect on the target |
|---|---|---|
| Router failure | `POST /router-failure` `{"node_id"}` | node `status = failed` (its links are kept but unusable) |
| Link failure | `POST /link-failure` `{"link_id"}` | link `status = failed` (link kept) |
| Packet loss | `POST /packet-loss` `{"link_id","packet_loss"}` | `packet_loss = value` (0–100 %) |
| Latency | `POST /latency` `{"link_id","latency"}` | `latency = value` (ms, ≥ 0) |
| Bandwidth reduction | `POST /bandwidth-reduction` `{"link_id","bandwidth"}` | `bandwidth = value` (Mbps, > 0) |
| Network congestion | `POST /congestion` `{"link_id","latency_increase","bandwidth_reduction_percent","packet_loss"}` | `latency += x`, `bandwidth *= (100 − pct)/100`, `packet_loss += y` (capped at 100) |
| Multiple failures | `POST /multi-failure` `{"events":[{"type": ..., ...}]}` | all events applied as one experiment |
| Generic | `POST /apply` `{"scenario","target_id","parameters"}` | any of the above (`multi_failure` takes `parameters.events`) |

Every apply endpoint also accepts optional `experiment_name` and `description`, and returns **201** with the experiment
and its events (each with `previous_state` and `new_state`). The specialised endpoints and `/apply` share one code path.

Management endpoints:

| Method | Path | Purpose |
|---|---|---|
| GET | `/active` | active experiments |
| GET | `/history` | every experiment, newest first |
| GET | `/{experiment_id}` | one experiment with its events |
| POST | `/{experiment_id}/revert` | revert one experiment (idempotent) |
| POST | `/reset` | revert every active experiment → `{"network_id","reverted_experiments","status":"reset"}` |

```bash
J='-H content-type:application/json'; API=http://localhost:8000/api/networks/net_001/chaos
curl -XPOST $API/latency $J -d '{"link_id":"link_002","latency":200}'
curl -XPOST $API/packet-loss $J -d '{"link_id":"link_002","packet_loss":30}'
curl -XPOST $API/congestion $J -d '{"link_id":"link_003","latency_increase":50,"bandwidth_reduction_percent":40,"packet_loss":10}'
curl -XPOST $API/multi-failure $J -d '{"events":[
  {"type":"link_failure","link_id":"link_001"},
  {"type":"packet_loss","link_id":"link_002","packet_loss":25},
  {"type":"latency","link_id":"link_003","latency":200}]}'
curl -XPOST $API/apply $J -d '{"experiment_name":"High Latency Test","scenario":"latency","target_id":"link_003","parameters":{"latency":200}}'
curl $API/active ; curl $API/history
curl -XPOST $API/chaos_001/revert ; curl -XPOST $API/reset
```

`GET /active` returns, per experiment, `experiment_id`, `scenario`, `target`, `status` and its `events`; for a single-event
experiment the scenario's parameters (`packet_loss`, `latency`, ...) are also repeated at the top level.
A `multi_failure` experiment has `target: "network"` and lists its child events.

Errors use the usual `{"error": {"code", "message"}}` shape:
**400** `invalid_packet_loss` (outside 0–100), `invalid_latency` (negative), `invalid_bandwidth` (≤ 0),
`invalid_bandwidth_reduction` (congestion percent outside 0 to < 100), `invalid_latency_increase`, `invalid_scenario`,
`invalid_target_id`, `invalid_events`, `invalid_parameters`;
**404** `network_not_found`, `node_not_found`, `link_not_found`, `experiment_not_found`;
**409** `node_already_failed`, `link_already_failed`.
A failed request changes nothing and leaves no experiment behind.

## 3. State management (the decision)

**Effective state is recomputed from the active chaos events** ("layered chaos state"). Every node/link has a *baseline*
(its configuration before any active chaos touched it). Each active event is a small deterministic operator, and

```
effective state = fold(operators of the ACTIVE events on that target, oldest first, starting from the baseline)
```

The `nodes`/`links` rows always hold the *effective* state (that is what the graph and Module 2 read), and are rewritten
after every apply/revert. Operators: failures set `status`; packet loss / latency / bandwidth reduction are **absolute**
(the newest active one wins); congestion is **relative** (it stacks on whatever is below it). All results are rounded to
6 decimals, so everything is exactly reproducible.

Why this and not "save the old value and put it back": with overlapping experiments, restoring an old value on revert is
wrong whenever another experiment is still active.

```
baseline latency 10
chaos_001: latency = 100      -> 100
chaos_002: latency = 200      -> 200
revert chaos_001 (oldest)     -> 200   (chaos_002 is still active; NOT put back to 10)
revert chaos_002              -> 10    (the original, not 100)
```

Reverting in any order gives the right answer, and once the last event on a target is gone the target is back to exactly
its original values. Congestion and packet loss layer the same way (`test_stacked_congestion_reverts_one_layer_at_a_time`).
Different properties of one link (latency + loss + failure) coexist and are reverted independently.

## 4. Database schema

Two new collections (created on first write; nothing existing is altered).

`chaos_experiments` (PK `id`, `network_id`; ids `chaos_001`… per network)

| Column | Notes |
|---|---|
| `id`, `network_id`, `name`, `description` | |
| `scenario_type` | the scenario, or `multi_failure` *(extra column; the experiment history needs it)* |
| `status` | `active` / `reverted` (`pending`, `failed` exist in the enum but are reserved, see §9) |
| `created_at`, `started_at`, `ended_at` | UTC |

`chaos_events` (PK `id`, `network_id`; ids `evt_001`… per network, and the number is the layer order; FK to experiment, cascade)

| Column | Notes |
|---|---|
| `experiment_id`, `scenario_type`, `target_type` (`node`/`link`), `target_id` | |
| `parameters` (JSON) | e.g. `{"latency": 150}` |
| `previous_state` (JSON) | the target's **original** state before any active chaos; events layered on one target share it |
| `new_state` (JSON) | effective state right after this event (audit snapshot; never used to restore) |
| `status`, `created_at`, `started_at`, `ended_at` | |

Neither table has a foreign key to nodes or links (their ids are never reused, and deleting a node must not delete history).

## 5. Revert, reset and idempotence

`POST /{experiment_id}/revert` marks the experiment's events `reverted`, then recomputes every target they touched from the
events that are *still* active, all in one transaction. Reverting an already reverted experiment returns **200** with
`already_reverted: true` and changes nothing; an unknown id is **404**. `POST /reset` does the same for every active
experiment of the network. If a node/link was deleted while chaos was active, reverting simply skips it.

## 6. Multi-failure experiments and transactions

`/multi-failure` creates **one** experiment (`chaos_00N`) with one event per entry. Applying is atomic: one database
transaction, and the NetworkX graph is only updated after the commit succeeds. A 404 (unknown target), 409 (e.g. the same
link failed twice in one request) or an unexpected error halfway through rolls everything back: no row changes, no
experiment is recorded, the graph is untouched. If the graph update itself ever fails, the graph is rebuilt from the database.
The graph is loaded from the values re-read from the database, so both always agree.
(`multi_failure` and target type `network` are experiment-level: the child events use the concrete scenarios.)

## 7. How chaos interacts with traffic simulation

`TrafficSimulator` is not given any chaos results; it reads `bandwidth`, `latency`, `packet_loss` and `status` from the
current graph, as before, so changed values show up in the very next simulation. One behaviour changed so that failures are
reported instead of silently worked around: the route is now calculated over the **whole** topology (failed elements
included) and then checked. If it crosses a failed node or link the simulation is stored as `failed`,
`route_available = false`, with the reason **`Current route contains failed node`** or **`Current route contains failed link`**.
Even if a detour exists it is **not** used (that is Module 5). Before this change the simulator skipped failed elements when
routing, which would have quietly rerouted traffic in any topology with a second path. A router failure does not touch its
links' rows; a link is unusable because its router is on the route.

Real run (Client-A – Router-B – Router-C – Server-D, every link 100 Mbps / 10 ms / 0 %, 100 packets × 1024 B, seed 42; chaos on the B–C link):

| Step | Status | Path latency | Packet loss | Throughput |
|---|---|---|---|---|
| Baseline | completed | 30 ms | 0 % | 21.27 Mbps |
| B–C latency = 200 ms | completed | **220 ms** (30 − 10 + 200) | 0 % | 3.59 Mbps |
| + B–C packet loss = 30 % | completed | 220 ms | **28 %** (28 packets dropped) | 2.58 Mbps |
| + B–C failed | **failed**, `Current route contains failed link` | – | – | – |
| Reset all chaos | completed | 30 ms | 0 % | 21.27 Mbps (identical to baseline) |

The numbers depend on the topology and seed; nothing is hard-coded (the final row is asserted equal to the baseline in the tests).

## 8. Dashboard

Sidebar: **Chaos Control** (the scenario picker changes the fields shown; *Multiple Failures* builds a batch with "Add to batch")
and **Active Chaos** (per-experiment *Revert Experiment*, plus **RESET ALL CHAOS**). A **Chaos History** table sits under the
topology. On the topology a failed router is greyed with a red ✕ and a FAILED label, a failed link is red and dashed
("✕ FAILED"), links of a failed router are grey dotted ("unavailable"), and a degraded link is orange and shows
`bandwidth · latency · loss`. Chaos does not re-run traffic: create and run a simulation afterwards, as before.

## 9. Design decisions, limitations and what is NOT implemented

- **Not implemented, on purpose:** failure detection (Module 4), automatic recovery and rerouting (Module 5), resilience
  scoring, a comparison engine (the data is there: each stored simulation has its metrics), WebSockets, timed/scheduled chaos.
- `router_failure` accepts any node id (a failed host or server is also useful); the dashboard offers routers only.
- Values are set as given: a "bandwidth reduction" to a value *above* the original is accepted (the spec only asks for `> 0`).
  Congestion's `packet_loss` is *added* to the link's loss (percentage points, capped at 100).
- `pending` and `failed` are valid statuses in the model, but applying is atomic, so no row is ever committed in either state today.
- Revert works per experiment, not per event.
- Deleting a node or link (Module 1) while chaos is active leaves its events `active` until you revert/reset; that is harmless.
- Same single-process limitation as before (the graph is process memory). Chaos edits take the network's row lock
  (a per-network in-process lock) so concurrent requests to one process are serialised.
- The automated tests run on mongomock by default; set `NETCHAOS_TEST_DB=real` (and a `MONGODB_DATABASE` starting with `netchaos_test`) to run them against a real MongoDB.

## 10. How Module 4 (failure detection) can consume the current state

Detection needs no new data source: `TopologyService(db, graph_manager).snapshot_graph(network_id)` gives node/link `status`,
`latency`, `bandwidth` and `packet_loss` (compare them to a link's original values in `chaos_events.previous_state`, or to a
threshold). `GET /chaos/active` lists what was injected and `TrafficSimulator.analyze_route()` returns
`available`, `reason`, `blocked_route`, `failed_nodes` and `failed_links` for a route that cannot be used, and Module 5 can build on the
same fields. Detection should compare *observed* metrics against a baseline instead of reading the chaos tables, otherwise it
would only detect what it was told about.

## 11. Tests

`pytest` runs the whole suite (194 tests). Module 3 adds `tests/test_chaos_state.py` (pure maths) and `tests/test_chaos_api.py`
(router/link failure, packet loss 0/10/50/100 and −1/101, latency, bandwidth, congestion, multi-failure incl. rollback,
exact revert, idempotence, reset, overlapping chaos, generic apply, 400/404/409 cases, graph and database agreement,
no rerouting, and the full A–B–C–D acceptance scenario).

# Module 4 — Failure Detection

## 1. Why a baseline is needed
Failure Detection dynamically assesses network health by comparing its active state against a previously defined healthy state (a baseline). Since networks can contain links with natively low bandwidth or high latency, absolute values don't determine degradation reliably. Comparing against the explicit baseline avoids false positives. 

## 2. How failures are detected
- **Node Failures:** Comparing current node `status` against the baseline.
- **Link Failures:** Comparing current link `status` against the baseline.
- The `FailureDetector` utilizes an `active_graph` mapped via NetworkX containing only active topology objects (filtering out failed components) to infer macroscopic failures.

## 3. How degraded links are identified
Even if status isn't `failed`, if `packet_loss > baseline.packet_loss + X`, `latency > baseline.latency * 1.X`, or `bandwidth < baseline.bandwidth * 0.X`, the link forms a `link_degradation` warning. These thresholds evaluate network usability without dropping connectivity entirely.

## 4. How connectivity is calculated
`NetworkX.has_path` is leveraged strictly over the filtered `active_graph` to verify whether structural reachability implies a valid connection between pairs at the current point in time given multiple link/node failovers.

## 5. How partitions are detected
Partitions occur when the underlying topological graph fractures. Leveraging `nx.connected_components()` against the undirected operational graph, the algorithm counts disjointed node assemblies. If `connected_components > 1`, a network partition is formally reported.

## 6. How affected traffic is identified
Traffic paths utilized in previous *completed* simulations (persisted via Module 2) are traced over the *current* network topology. If the route directly depends upon a node or link that is currently flagged as `failed` or `degraded`, the simulation flows are immediately flagged as structurally impacted or unavailable.

## 7. API Endpoints
| Method | Path | Purpose |
|---|---|---|
| POST | `/api/networks/{network_id}/failures/baseline` | Captures baseline |
| GET | `/api/networks/{network_id}/failures/baseline` | Gets baseline |
| POST | `/api/networks/{network_id}/failures/detect` | Runs and persists failure detection sweep |
| GET | `/api/networks/{network_id}/failures/report` | Gets latest generated failure sweep report |
| GET | `/api/networks/{network_id}/failures/history` | Detections history |
| GET | `/api/networks/{network_id}/failures/connectivity` | Checks point-to-point structural connectivity |
| GET | `/api/networks/{network_id}/failures/affected-traffic` | Computes list of earlier traffics impaired by the latest faults |

## 8. Example Detection Report
```json
{

  "detected_at": "2026-10-04T12:00:00Z",

```

## 9. What Module 4 does NOT do
Module 4 restricts itself strictly to diagnostics and observability. It does **not** perform automatic recovery, dynamic rerouting (path-switching traffic away from failures), topology component healing, or calculate "Resilience Scores." It exclusively diagnoses failures spawned by Module 3. Actions resulting from these evaluations denote Module 5.

# Module 5 — Dynamic Recovery

Dynamic recovery is a crucial aspect of resilient networks. When a failure occurs, the network must adapt by rerouting affected traffic via an available alternative route while maintaining the visibility of the failed components.

This module adds dynamic traffic recovery capabilities.

## What it does

When a chaos event makes an existing traffic route unavailable, this module is responsible for identifying an alternative path using an operational graph (a view of the topology with failed nodes and links excluded), evaluating and selecting a valid route, and updating the active simulations to use the newly discovered path. Note that the failed components are not repaired; only the traffic gets rerouted around the failures. 

## How it works

1. Traffic is running on a normal route.
2. A chaos event disrupts a link or node.
3. The Failure Detection module identifies the disruption.
4. The Dynamic Recovery engine analyzes the operational topology graph, avoiding failed links and nodes.
5. It computes the best valid alternative route using a selected routing strategy.
6. The simulation is updated with the recovered route and metrics.

## Workflow Diagram

```text
Failure
   ↓
Detection
   ↓
Affected Traffic
   ↓
Alternative Route
   ↓
Route Selection
   ↓
Traffic Rerouting
   ↓
Recovery Metrics
```

## Supported Strategies

- `shortest_hop`: Selects the route with the fewest links using BFS.
- `lowest_latency`: Selects the route with the minimum total link latency.
- `highest_bandwidth`: Identifies routes with the maximum bottleneck bandwidth.
- `composite`: A customizable weighted scoring based on hops, latency, and bandwidth.

## APIs

- `POST /api/networks/{network_id}/recovery`: Attempt to find an alternative route for a single disrupted simulation.
- `POST /api/networks/{network_id}/recovery/all`: Attempt recovery for all completed simulations currently affected by failures.
- `POST /api/networks/{network_id}/recovery/preview`: Calculate a candidate alternative route for preview purposes without updating database state.
- `GET /api/networks/{network_id}/recovery/history`: List all recovery events for a network.
- `GET /api/networks/{network_id}/simulations/{simulation_id}/route`: Fetch the current state of a route for a specific simulation.

## Recovery Metrics

When a route is recovered, metrics from the initial configuration and the post-recovery route are saved in the database for comparison. These include:
- `original_latency` & `recovered_latency`: Total latency sum of properties across respective routes.
- `original_hop_count` & `recovered_hop_count`: Number of hops via length calculation.
- `original_bandwidth` & `recovered_bandwidth`: The performance constraints derived from the bottleneck bandwidth.
- `recovery_duration`: The execution time required to calculate and finalize the alternative.

```text
A → B → D

B-D FAILED

Recovered:
A → C → D
```
